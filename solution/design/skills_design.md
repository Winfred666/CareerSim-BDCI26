# CareerSim 解决方案设计思路文档

> 对应实现：`solution/skills/observe-decide-review` v4.7.5，manifest `mode: team`
>
> 本文阐述总体设计思路与关键取舍；逐轮决策的完整流程、判据与数值依据见同目录 `decision_report.md`。

## 一、总体架构

48 个月的职业模拟中，真正稀缺的是两样东西：**语义判断的准确性**与**长程决策的一致性**。前者无法用规则穷举——事件以自然语言给出，同一种表述在不同前情下对应的指标含义会漂移；后者无法依赖模型的记忆维持——判断依据、甚至各项收益加减法心算的准确性，都会随事件累积而稀释，跨季度的目标极易被眼前的局部收益挤掉。

方案据此确立一条贯穿全文的分工原则：**把「读懂事件」交给 AI，把「算清后果」交给脚本，把「交接状态」交给文件。**

在此原则下，方案有五点区别于常规多 Agent 做法的设计主张：

1. **专家并行翻译承担绝大多数事件**——五个指标专家 teammate 以专一上下文并行完成语义量化，彼此不通信、不看见游戏历史；交互形式被压到最小粒度的问卷，脚本在每次提问时注入当前事件与判定标准，使模型只能在「此刻这道题」的语境下作答。
2. **决策置信度分析实现事件分流与补救**——为翻译误差建立分布模型，量化每个推荐的决策稳定率。稳定率足够高的事件由符号策略推荐编号，Leader 执行；稳定率不足的少数事件，系统主动放弃推荐，把原题与前情完整交回 Leader 做整体语义判断。专家接管多数、语义纠偏兜住少数，构成分流与补救的分工。
3. **语义与符号彻底分离**——AI 只回答「这段文字对应多少指标增量」，不做模糊规划与比较；全部状态约束、优先级策略由确定性 Python 承担，并向 Agent 输出量化提示词。Agent 之间只经文件交接，减少自然语言磨损。
4. **红线约束写入脚本**——生存约束是硬的条件分支，任何维度的收益都不能换取对低位指标的削减；即使做语义纠偏，红线提示词依然生效。
5. **有界自进化**——问卷可依历史误判自我修订，但触发条件、改动幅度与改动范围全部由脚本强制约束，防止自我进化退化为过拟合。

由于任务被切成六个输出皆为量化值、且都有官方真值可对的模块（O / N / S / HW / R 五个翻译器与一个量化决策脚本），这套方案还可以脱离完整的 career-emulator 做高速并行迭代——详见第七节 7.4。

整体采用 **JiuwenSwarm team 模式**：一个 Leader agent 统筹主循环，五个 teammate agent 并行完成各指标的语义量化翻译，Python 脚本系统承担全部状态管理、约束检测、前瞻规划与决策计算。

```
Leader
 ├─ 初始化 (new_game → workflow-state.py create_new)
 └─ 循环 observe → dispatch → decide → review → observe
          │          │
          │     dispatch.py → spawn 新组 → shutdown 上一组 → 并行 DM
          │     ├── o-<事件编号>  (Output 指标预测 teammate)
          │     ├── n-<事件编号>  (Network 指标预测 teammate)
          │     ├── s-<事件编号>  (Skill 指标预测 teammate)
          │     ├── hw-<事件编号> (Health / Wealth 指标预测 teammate)
          │     └── r-<事件编号>  (Risk 隐藏指标预测 teammate)
          │
          └─ 脚本汇总 → read-context.py → 推荐编号 or 语义纠偏包
```

**协作数据流的唯一入口是文件。** Agent 之间不传递任何自然语言结论，只通过脚本读写 `notebooks/` 目录下的结构化文件（TSV、JSON）交换信息。这一约束消除了多 Agent 自然语言交接固有的歧义与复述损耗，同时使每一轮的完整状态都可从磁盘复原——这既是资源优化的来源（第七节），也是失败恢复的基础（第六节）。

## 二、Skill 设计与职责边界

### 2.1 能力划分

方案只设一个 swarm-skill（`observe-decide-review`），不拆成多个 Skill。原因是主循环各阶段共享同一份状态与同一套红线判据：一旦拆分为多个 Skill，本应完成的一致性校验就会退化成跨 Skill 的协商问题，既增加 Token 开销，也引入状态漂移的风险。

Skill 内部按「语义—符号—交接」三层划分能力，并在 manifest 中声明 1 个 Leader 与 5 个 teammate 角色：

| 角色 | 承担职责 | 明确不做的事 |
|---|---|---|
| Leader | 调用游戏 API、并行派发翻译任务、采纳决策结果、记录复核 | 不做指标语义翻译 |
| 5 个 Teammate | 各自负责一个指标组的问卷作答，输出结构化增量 | 不选择游戏行动，不与其他成员通信 |
| Python 脚本 | 全部符号计算：状态流转、红线检测、前瞻规划、排序、异常提醒 | 不做任何自然语言语义判断 |

### 2.2 职责边界的两条硬约束

**1. Teammate 仅在收到 Leader 指派时激活，且只能看见自己的世界。** 每个 teammate 的上下文只包含自身角色文档与当前事件的题目，读不到 SKILL.md、其他角色文档与任何源码；作答结果直接写入共享文件，不向任何其他角色发消息。看得越少，越不会「脑补」事件之外的因果。

**2. 脚本不做语义判断，AI 不接触符号逻辑。** 边界是双向的：脚本负责观察后刷新指标状态、汇总各选项的预测增量、执行红线过滤与前瞻排序、校验行动日志并推进工作流阶段；而这一切的输入——各选项的指标增量——只能来自 AI 的问卷作答或平台给出的官方数值。语义与符号之间只有结构化数据这一个接口，没有任何一方能越界替另一方做判断。

### 2.3 问卷化交互：把语义判断压到最小粒度

翻译 teammate 与脚本之间的交互不是自由对话，而是**一问一答的问卷**。脚本逐题发问，模型每次只返回一个选项编号或一个小幅整数；题目之间的推进、分支与终止全部由脚本控制。

这一形式带来三项无法靠提示词获得的性质：

- **上下文始终新鲜。** 每一道题都由脚本在提问时现场注入当前事件文本、当前状态与该指标的判定标准。模型面对的永远是「此刻这一道题」，而不是几十轮之前读过的题面；事件切换、职级变化与判定标准修订都会立刻反映到下一次提问中，不存在陈旧语境残留。
- **回答被迫科学化。** 问卷把一个笼统的「这个选项对 O 有什么影响」拆成若干必须先答的中间判断——成果是否已落地、增益来自何处、是否附带额外负担、净方向为何、幅度多大。每一步都是可核对的小断言，误判因此可归因到具体某一题，而不是淹没在一个总分里。
- **输出天然结构化。** 问卷的终点就是一个受值域约束的整数，无需再从自然语言中抽取数字，也就没有抽取失败这一类错误。

代价是问题数量增多。方案的取舍是明确的：**宁可多问几道可核对的小题，也不要一个无法追溯的整体判断**——因为后者一旦出错，没有任何机制能发现它。

## 三、长期规划机制

方案把长期规划通过脚本，每轮重复输出给 Agent，而不放进任何 Agent 的 skill 文件 —— 长期目标因此在每一次事件判断都位于新鲜的上下文中。本节逐层说明目标如何被拆解到每一轮行动，以及拆解的结果以什么形式交付给 Leader。

### 3.1 晋升路径建模：以缺口驱动短板补强

系统按职级晋升所需的资格给决策打分。每次决策前，把当前 S/O/N 与下一职级的要求逐项比对，得到一组带符号的缺口，并按缺口位置分级定价：**最大缺口权重最高，其余缺口次之，资格已全部满足后的额外储备几乎不计价**。这一梯度使行动自动流向最短板。

反向定价同样不对称：扩大缺口的惩罚重于同等幅度的正向奖励；已达标后跌破资格线另有追加惩罚；而当资格已全部满足、距下一次评审仅剩一个月时，任何下降都会被重罚——它毁掉的是一次已经到手的晋升机会，代价不能按普通指标波动计算。

系统同时按职级推算各项指标的目标配比，并在半年谈话、绩效奖金与晋升通知后把当时的状态与反馈记入台账，用于校验实际晋升与推算之间的偏离。决策侧只消费「当前缺口」这一项，台账侧则构成长期规划的一致性证据链。

### 3.2 季度行动搜索：体力与主行动的组合前瞻

每季度可执行至多三次体力行动加一次主行动。若逐个贪心选择，很容易把体力花在当下最优、却挤掉后续更优组合的选项上。方案在脚本内做有限深度的组合枚举：以整个季度的行动序列为搜索空间，对每个终态以统一目标（考核前瞻，或收官阶段的整体价值度量）评分，返回最优序列的**第一步**。

行动执行后重新规划，因此每一步都在同一个终点上重新对齐——这正是「跨季度行动一致性」的实现方式：**不依赖承诺既定计划，而依赖每步都对同一目标重新求最优**。搜索全程保持红线约束，任何会导致淘汰或风险失控的中间态都被直接剪枝。

对 Leader 而言，这一切只体现为「每次提交一个合法编号，完成后继续分配剩余体力」。前瞻完全在脚本内完成，不增加任何 Agent 侧的认知或 Token 负担——这是「算清后果交给脚本」这一分工原则最直接的收益。

### 3.3 最简量化决策包：长期规划如何交付到 Leader 手上

上述所有推演——资格缺口、季度组合、红线状态与风险轨迹——最终都被压缩成**一个只含结论的决策包**交给 Leader：当前状态摘要、通过红线过滤的候选、推荐编号，以及一句可直接提交的 notes。原始事件文本、翻译过程、中间投影与打分细节一概不进入 Leader 上下文。

这一交付形式正是长期规划得以成立的关键，理由有三：

- **一致性由单一来源保证。** 每轮决策包都由同一份脚本、基于同一份落盘状态生成，跨季度的目标不会因上下文更替而漂移；
- **认知负荷与局数无关。** Leader 既不需要理解、也不允许改写定价逻辑，它的工作是「调用工具、原样执行、完成复核」，因此第 48 月的决策输入与第 1 月同样干净；
- **例外同样结构化。** 当脚本判定不宜直接推荐时（5.4），交回的不是含糊的提示，而是一份带明确约束的纠偏包：原题、前情、原始选项与「哪些指标不得削减」。降级路径与正常路径共用同一种交付形态。

换言之，长期规划并不以「计划文档」的形式存在于任何 Agent 的记忆里，它以**每轮重新求解、并以最简量化形式交付**的方式存在。这既解释了方案为何能在 48 个月里保持目标一致，也解释了 Leader 的上下文为何能长期维持在很小的规模（实测见 7.1）。

### 3.4 决策一致性保障

长期规划要成立，前提是每一步决策都建立在同一份可信状态上。系统在决策前校验本轮所有指标翻译均已完成、各份回执确实对应当前事件与当前版本的问卷，并在读取决策包前后各校验一次关键状态文件的字节，防止基于过期或不一致的翻译结果做出行动（机制细节见 6.3、6.5）。

这一层的价值在长局中才被放大：48 个月里任何一次「用上一版问卷的答案回答这一版的题」都不会报错，只会静默地把此后所有轮次的排序带偏。

## 四、框架运用

框架能力的取舍标准只有一条：**它是否让语义判断更准、让长程决策更稳**。凡符合这一标准的——team 模式、teammate 上下文隔离、并行指派——方案充分使用；凡与之无关、或可由确定性脚本更好覆盖的——流程编排 DSL、任务校验、层级化分发、成员计划环节——一律主动关闭。以下逐项说明理由。

### 4.1 team 模式的选用理由

选用 team 模式而非单 agent，核心原因有三：

**指标翻译在语义上彼此独立。** O/N/S/HW/R 五组指标的判断原则各自成立、互不依赖，天然适合并行。单 agent 串行答题会不断累积上下文，极易在跨指标语义间产生干扰——例如把 H 的「持续耗损才算损失」这一判断逻辑带入 O 的「只看已落地成果」。

**上下文隔离带来判断纯度。** 每个 teammate 只持有自己的角色文档与当前事件题目，避免 Leader 的完整游戏历史污染指标判断——这一点对翻译质量的影响是结构性的。

**并行压缩等待时间。** 五个 teammate 同时作答，总等待时间取决于最慢者，而非五者之和。

至于框架提供的 SwarmFlow 编排能力，方案有意不使用：本场景的编排逻辑（派发—等待—汇总—校验）具有强状态依赖与严格的一致性要求，用确定性 Python 脚本实现比用编排 DSL 表达更可控，也更省 Token。

### 4.2 teammate 启动与上下文隔离

每个需要翻译的事件都使用一组全新成员。Leader 进入派发阶段只运行一个无参数的 `dispatch.py`，按返回顺序调用原生工具：成员名由脚本依事件编号生成并落盘，Leader 不计数、不自行拼名；每次派发先建齐新组、再关闭上一组，避免团队在切换瞬间因没有非 Leader 成员而被自动清空。官方已给出数值的事件直接跳过派发，但下一次翻译仍会关闭上一次实际使用的成员。

换新成员而不复用旧成员，是为了让每个事件都从一份干净上下文开始：旧成员的对话检查点里留着上一场事件的题面与作答，复用等于把陈旧语境带进新判断。代价是成员记录随事件数累积，因此成员名被压到最短、描述留空，使 roster 的文本开销可以忽略。

派发序列由脚本一次性给出，Leader 必须完整执行；任何一步失败即停，不能靠重跑脚本来接续一段只完成了一半的序列——重跑会重建名单，反而掩盖真正的失败位置。

### 4.3 最小化协作消息

Leader 向每个 teammate 发送的指派消息，其内容就是本轮成员名本身（如 `o-1`），收件人与正文都由 `dispatch.py` 生成。**成员名即触发信号**：teammate 收到后按角色文档执行，结果写入共享文件，不向任何成员回复消息、不提交轮次报告、不输出最终文本。

这使协作消息的信息量趋近于零，也从根本上排除了成员之间通过自然语言相互影响判断的可能。

### 4.4 等待与决策合并

Leader 发出五条并行指派后，只执行一次等待命令（`workflow-state.py wait`）。该命令轮询所有翻译结果，全部到位后**默认汇总各选项的预测增量并返回本轮决策包**（推荐或纠偏），无需额外参数或单独调用 `read-context.py`。等待与决策包读取合并为一次操作，每个事件节省一次 Leader 工具调用往返。

### 4.5 主动关闭的框架能力

`build_team` 时显式设置 `enable_hitt: false`、`enable_task_verification: false`。理由是这两项能力解决的问题，本方案已由确定性脚本更好地覆盖：任务校验由回执哈希与阶段前驱校验完成（6.3），层级化任务分发由固定角色表完成。保留它们只会带来额外的 Token 开销与不确定的交互轮次，而收益为零。

`teammate_mode` 采用 `build_mode`：成员不需先提交任务计划再执行，因为任务内容（当前事件的问卷）已由脚本完全确定，计划环节没有可决策的空间。

## 五、风险控制

### 5.1 生存红线（即时淘汰防护）

健康 H ≤ 3、尊严 D ≤ 3、财富 W ≤ 2 时，对应指标进入低位保护状态。所有预测会进一步削减已处于低位指标的选项被无条件排除——**即使只削减 1 点，即使其他维度收益极大**。

该过滤在所有排序之前执行，且不可被绕过：领导的明确要求、情节压力、其他指标的高额收益，都不构成例外。当所有选项均触线、过滤后候选为空时，系统不返回推荐，而是转入语义纠偏路径（5.4），把原题与「禁止选择会削减这些指标的行为」这一约束一并交回 Leader 独立判断——**红线本身并未放宽，只是改由人在明知约束的前提下做选择**，而不是由脚本机械地挑一个损失最小项。

### 5.2 多层决策优先级

在通过红线过滤的候选中，依次按以下维度排序，前一维度相同才比较后一维度：

1. 压低职业风险（R > 1 时优先降险）
2. 补足已处于低位的指标
3. 补晋升短板（缺口最大者优先）
4. 其他正增益，优先投向仍有成长空间的指标

前三层是安全性与资格性约束，第四层才是收益优化。这一顺序保证了「先活着、再合格、后最优」，任何收益都无法赎买前三层的损失。

### 5.3 职业风险（R）管理

R 是唯一的隐藏指标：平台不提供读数，估算偏差却会直接导致淘汰，是全局不确定性最高的一项。方案不指望单次估算准确，而是用三重机制让误差能被外部证据持续校正：

- **专门角色估算**：由 `translate-r` 独立判断每步行动带来的职业暴露变化，判据刻意从严——降低风险必须对应已落实的具体保障，普通努力、态度转变或口头表态一律不算防护；明确违法、造假或欺骗审查的行为，不因领导授意或指标收益而判为安全。宁可高估风险，也不把一次侥幸当成可复用的结论。
- **官方档位锚定**：平台会在 HR 反馈中给出官方风险档位，系统优先以官方读数覆盖估算值，使 R 定期被真实评价拉回，误差不跨月累积。
- **月内回放与爆雷重置**：两次官方读数之间，以最近一次档位为起点累加本月已执行动作的变化；公开日志一旦显示隐患爆雷即按规则重置，只累计其后的动作。爆雷次数直接进入绩效推演，因此已爆雷状态下的高风险被视为不可接受。

三重机制的分工是明确的：**估算负责月内精度，官方锚定负责跨月纠偏，回放负责把两者拼接成一条连续的风险轨迹**。R 的角色问卷不开放自进化修改（7.3）——隐藏指标没有公开真值，允许自我修订只会放大偏差。

### 5.4 决策置信度分析：事件分流与语义纠偏

风险控制的最后一层，是承认**符号策略自己也会错**。翻译来自 AI 的语义判断，单项增量只有几个整数的取值范围，一处方向误判就足以翻转排序；而在晋升资格附近，1 点偏差直接决定一次晋升是否成立。方案因此不把翻译结果当作确定输入，而是显式建模其不确定性，并据此把每一个事件分流到两条不同的处理路径上。它与「专家并行翻译」（4.1）配对后才成立——前者负责把大多数事件判准，后者负责在判不准时不硬判。

**分流判据一：决策置信度不足。** 系统为翻译误差建立条件分布模型，对一个事件采样多组误差情景，在每组情景下**完整重跑**红线过滤、考核前瞻与季度搜索，统计名义推荐是否仍然最优，得到**决策稳定率（决策置信度）**。稳定率足够高，说明推荐对翻译误差稳健，直接由符号策略给出编号，Leader 原样执行；稳定率低于 0.5，说明结论高度依赖某几处可能出错的语义判断，系统主动放弃推荐。采样方式与判据见 `decision_report.md` 第三节。

**分流判据二：结构性死局。** 出现以下任一情形时同样放弃推荐：所有选项均预测触发淘汰；整场事件为纯负面翻译（所有选项均无正增量、且 R 无下降）；或所有并列最优候选均会破坏已经满足的晋升资格。这三类局面有一个共同特征——**它们本不该出现**；一旦出现，最可能的解释就是翻译存在方向性偏差。与其输出一个「损失最小的坏选项」，不如把事件交回语义层重新判断。完整定义见 `decision_report.md` 第三节。

**补救方式：交回原题，而不是交回带噪的数字。** 两类条件触发后，脚本返回**原题、前情、原始选项与仅按当前状态计算的约束**，由 Leader 依据事件完整文本独立判断，并自行用一句简短的行为理由填写 notes。此处刻意**不返回**带误差标注的预测增量、不返回排名与净值——低可信度的数值一旦给出，就会成为锚定 Leader 语义判断的先入之见，反而使补救失效。

这套机制的收益是双重的：

- **绝大多数事件由专家路径低成本处理。** 置信度足够时，Leader 只收到一个编号与一句 notes，不必阅读任何事件文本，认知负荷与 Token 开销都压到最低（实测见 7.1）；
- **少数高风险事件获得语义层兜底。** 恰好在符号策略最可能出错的地方，由具备完整语境的整体判断接管，而不是让一个可疑的数字决定行动。

关键在于，**分流比例不是人为设定的常量，而是由误差模型在每个事件上实时算出**：局面越依赖可疑的语义判断，越会被送去纠偏；局面越稳健，越由脚本直接接管。风险控制的资源因此被自动配置到最需要它的地方。

需要强调的是，置信度为 0 的含义是「符号策略放弃直接推荐」，而**不是**「所有选项必然有害」。且无论走哪条路径，H/D/W 禁减约束始终有效，不得放宽：**纠偏改变的是「由谁判断」，而不是「什么被允许」**。

### 5.5 财富与健康的时变定价

同一个数字在第 1 月和第 45 月的代价并不相同，把它当成常量是长局决策的常见失误。方案对两类资源做了显式的时变建模：

**财富损失随职级与月份双重放大。** 名义上的财富损失在投影时按职级缩放，职级越高放大倍数越大——低职级阶段可以为换取关键指标而承受财务损失，高职级阶段同等损失的折算代价极高，必须以守财为优先。在此之上另设一项随月份递增的损失折价，使「早期容错、后期保守」成为策略的内生倾向，而非依赖临场判断。

**健康的价值在收官阶段上升。** 最后阶段 H 的边际权重被显著放大，原因是此时已无后续评审可以恢复，健康只剩结局评价与存活两条价值路径，任何侥幸心理都不再成立。

两项调整都没有引入新的启发式规则，只是把「同一损失在不同时点的真实代价不同」这一事实写进了价值函数。

## 六、失败恢复

方案设计时预设了三类故障：**会话中断**（Leader 崩溃、进程重启、响应丢失）、**成员无响应**（teammate 超时未完成）、**状态不一致**（并发写入、过期回执、快照漂移）。此外还包括一类并非故障但同样棘手的局面：**无好选项可选**。以下机制分别对应。

### 6.1 工作流阶段管理

脚本维护一条从观察、翻译、决策、复核直至终局的明确阶段链，每次推进都在文件锁内完成，并校验前驱阶段确实处于允许状态，否则直接拒绝。并发写入与意外重入因此不可能把状态推进到一个非法位置。

由于全部状态都落盘，即使 Leader 崩溃重启，也能从磁盘推断出正确的续行点：恢复命令返回应当从哪个阶段继续，若翻译未完成还会**直接列出缺失的 teammate 名单**，Leader 无需自行排查。恢复前会逐项校验新的观察结果与挂起事件是否完全一致，不一致即报错，避免在错误的事件上续行。

### 6.2 翻译任务超时与重发

等待翻译完成设有超时。首次超时后，系统只提示 Leader 继续执行同一条等待命令、**不要重发消息**——多数情况下成员仍在作答，重发只会造成重复触发与上下文浪费。重试仍超时时，Leader 再次运行同一个无参数 `dispatch.py`；脚本复用本轮成员，核对回执后只输出未完成成员的 DM，不再建队或关队；角色不符或名单漂移一律拒绝，Leader 不自行拼接命令。

这一设计把「超时」与「失败」区分开：超时先假定成员仍在正常工作，只有二次超时才升级为定向重发，从而避免多 Agent 系统中最常见的一类浪费——因为一次网络抖动就把五个成员的上下文全部重建。

### 6.3 翻译结果完整性校验

汇总各选项的预测增量前，系统对每份回执做四重校验：观察是否属于当前事件、任务是否属于本轮、**问卷与角色文档的当前指纹是否与作答时一致**、已作答的选项集合是否恰好等于需要翻译的集合。任一不符即报错。

其中指纹校验尤为关键。指纹覆盖问卷定义、角色文档与自进化脚本本身，因此任何一次问卷修改都会立即让全部旧回执失效，从机制上排除了「用上一版问卷的答案回答这一版问卷的题」这类静默错误——而这恰恰是自进化机制（7.3）最容易引入的风险。此外，所有增量都被约束为小幅整数，越界即拒绝。

### 6.4 复核幂等性

复核脚本允许重复调用得到相同结果：写入行动回执前检查是否已存在相同记录，字段完全一致则安全重放，字段冲突则直接报错；台账中「待判定」的行同样支持重试，但重试结果必须与原始行动一致，否则报错——这避免了用一次重放悄悄改写历史。日志游标则保证单调性，已消费或被替换的日志不得再次复核。

幂等性的真正价值在于，它让「不确定上一次是否成功」有了一个安全的默认答案：**重放即可，不必猜测**。在没有这一层保障的系统里，Agent 面对不确定结局时往往只能选择重建状态或跳过写入，两者都可能造成不可逆的错误。

### 6.5 决策快照一致性

读取决策包时，系统在读取前后各校验一次全部关键状态文件的内容字节，若期间发生变化则报错并要求重新观察。这确保决策不会建立在一份被并发修改过的快照上——五个 teammate 与 Leader 同时读写同一目录时，这类竞争是真实存在的。

所有台账写入均采用「临时文件 + 原子替换」的方式，使任何一次写入要么完整生效、要么完全不生效，不存在中间态。

### 6.6 出错即停原则

除翻译等待超时按 6.2 的规则重试外，其余所有脚本错误一律立即停止。Leader 不自行调试、不搜索目录、不重放动作，只通过明确的错误信息交人工介入。

这条原则看似保守，实则是防止状态污染的必要取舍：在一个所有状态都由文件承载、且后续决策完全依赖历史状态一致性的系统里，让 Agent 自行「想办法绕过」一个错误，其代价远高于停止一局。

### 6.7 不利局面的降级路径

当异常不是来自系统而是来自局面本身——所有选项都是负面的、或决策置信度不足——降级策略即 5.4 的语义纠偏：放弃符号推荐，把完整原题与硬性约束交回 Leader 做整体语义判断，同时保持红线约束不放宽。这使方案在「无好选项」时仍能给出合法且不越线的行动，而不是机械地选择损失最小项。

## 七、资源优化与自进化机制

资源优化的目标不是把 Token 压到最低，而是**把每一分开销都花在语义判断上，不花在协调上**；同时让每一次迭代本身也足够便宜。以下依次给出对照实测、时间开销的三处压缩、运行时自进化，以及模块化切分带来的离线迭代效率。

### 7.1 Token 消耗实测：开销被搬到了哪里

方案在相同评测模式下完整运行了两组对照：**本方案**（脚本协同 + 5 个翻译 teammate）与**无翻译基线**（Leader 自行阅读事件并直接决策），数据取自运行日志的实测统计。需先说明口径：以下数字来自成员轮换改动前的固定成员版本，当前版本每事件多出建队与关队调用、roster 也会持续累积，其总 Token 与上下文增速尚待完整运行测量。

| | 本方案 | 无翻译基线 |
|---|---:|---:|
| 统计事件数 | 40 | 51 |
| 每事件总消耗均值 | **1932 k** | **672 k** |
| 叙事事件均值（需翻译） | 2530 k（28 个） | — |
| 官方已给数值事件均值（免翻译） | 593 k（12 个） | — |
| 叙事事件内 Leader 占比 | 638 k（25.2%） | 672 k（100%） |
| 叙事事件内 5 个 teammate 合计 | 1892 k（74.8%） | — |

**结论一：多出来的开销几乎全是判断，不是协调。**

本方案每事件消耗约为无翻译基线的 2.9 倍。这一倍数需要被拆开看，而不是被回避：

- 平台已给出官方数值、无需翻译的事件，本方案每事件仅 **593 k，低于基线的 672 k**——脚本直接采用官方增量并返回编号，Leader 连事件文本都不必读；
- 需要翻译的叙事事件为 2530 k，其中 1892 k 是五个 teammate 的问卷作答，Leader 自己只占 638 k；
- Agent 之间的协作消息内容就是成员名本身（4.3），协调开销在字面意义上趋近于零。

也就是说，多出的 Token **全部买到了语义判断**：每个指标由一个只看得见该指标判据与当前这道题的专家独立评估，而不是由一个背着数十个月历史的 Leader 顺手估一下。这笔交易是否划算，取决于翻译准确率对成绩的影响；而 5.4 的置信度分流正是为「可能不划算的那部分」准备的止损闸门。

**结论二：Leader 上下文增速更慢，且不触发平台压缩。**

| Leader 上下文 | 本方案 | 无翻译基线 |
|---|---|---|
| 第 1 个事件 | 51.1 k | 50.2 k |
| 第 10 个事件 | **71.1 k** | 77.9 k |
| 第 30 个事件 | **114.2 k** | 135.1 k |
| 第 39 个事件 | **134.0 k** | 159.9 k → 触发自动压缩，回落至 53.8 k |
| 每事件平均增量 | **+2.17 k** | +2.9 k |

两条曲线起点几乎相同，斜率却不同：本方案额外携带五个 Agent，Leader 上下文的每事件增量反而低约 25%。原因即 3.3 的最简量化决策包——每轮进入 Leader 上下文的只有结论，没有原始事件文本与观察历史。

差异更体现在压缩行为上。基线在第 39 个事件后达到 159.9 k 并触发平台自动压缩，早期历史被摘要化丢弃；而一局 48 个月约含 50–60 个事件，这意味着**基线在长局后半段是在一份被压缩过的记忆上做决策**。本方案在同等长度的窗口内未触发压缩，Leader 拿到的每一份决策包都是完整无损的。

此处需如实说明两点边界。其一，Leader 上下文并非全程恒定：它随事件数缓慢线性增长，且在语义纠偏轮次会因交回完整原题与前情而出现一次**主动支付**的阶跃（5.4）——这是换取判断质量的开销，不是可以消除的浪费。其二，上述数字取自固定窗口的运行日志，随机种子与事件分布不同会带来浮动，因此它们用于说明**结构与量级**，不宜被读作精确基准。

**综合结论**：本方案没有把 Token 省下来，而是把它从协调与历史维护**转移**到了语义判断上。每事件约 2.9 倍于无翻译基线的开销，换来的是五个专一上下文专家的独立评估、一条不触发压缩的 Leader 上下文曲线，以及一个能在翻译不可靠时主动弃权的风险闸门。评审关心的「开销与成绩之间的权衡」，在本方案中是一笔可核对的账：**贵在哪里、买到了什么、什么时候止损**，三者都有明确答案。

### 7.2 时间开销的三处压缩

- **并行翻译**：五指标并行，串行需 5 次 agent 往返，并行只需 1 次（以最慢者为准）；
- **等待与决策合并**：等待命令直接返回决策包，每个事件节省一次 Leader 工具调用往返；
- **有界历史读取**：自进化环节只要求 teammate 读取误判历史的末尾片段而非全量，使该项开销不随游戏进程增长。

三处压缩的共同点是：它们削减的都是**协调开销**，而不是**判断开销**。AI 该做的语义判断一次没少，省下的全是往返、等待与重复上下文。

### 7.3 自进化机制

每个指标翻译 teammate 在每轮开始时检查历史中是否出现过同类误判；若发现可归纳的典型错误，便在正式答题前对问卷做最小化修改（补充判断边界或修正方向偏差），再以更新后的问卷重新翻译。翻译质量因此在同一局内持续改善，且不增加任何额外的 Agent 往返。

自进化最大的风险是退化为过拟合——用一条特设规则去拟合一个偶发样本。方案的做法是把约束全部写进脚本校验，而不是写进提示词：

- **只有方向性误判才触发**：预测增大而实际减小，或反之。仅有幅度偏差的反馈被直接忽略，因为幅度噪声不值得为它改写判据。
- **改动范围被锁死**：只改单题的题面文案，不改取值、流程或算式；每次限于一处、长度有上限的短句，且被替换的原短句须在该题中唯一出现。
- **只增不减**：不得删除已有的有效边界，不得用冗杂表述拟合单一情境；归纳不出典型错误时允许明确跳过修改。
- **隐藏指标不参与**：职业风险 R 无公开真值，不开放问卷修改。

问卷修改按 session 隔离记录，写入前做乐观锁校验，避免基于过期版本编辑。

### 7.4 模块化离线迭代：不跑完整对局也能打磨方案

任务切分带来一项容易被忽略、却直接决定迭代速度的收益：**六个模块的输出都是量化值，且都有官方真值可对照**。O/N/S/HW/R 五个翻译器输出指标增量，官方日志给出实际增量；量化决策脚本输出推荐编号与预测状态，下一轮观察给出实际状态。于是每个模块都能脱离完整的 career-emulator 单独评测——而跑完一局 48 个月的模拟需要数千秒与上百 M Token，是整个迭代链路中最昂贵的一环。

方案因此把打磨过程拆成三条可并行运行的离线回路：

- **翻译器的通用性打磨。** 以历史事件为样本，逐指标统计「预测增量 vs 官方实际增量」的方向错误率与幅度偏差，把误判归类为可归纳的典型错误（例如「把态度转变判成能力增益」），再据此改写问卷中对应题目的判据边界。改动是否有效，由留出样本上的方向错误率判定，而非由某个印象深刻的案例决定——这与 7.3 的运行时自进化遵循同一套逻辑，只是在离线阶段以更大的样本量执行。
- **量化决策脚本的打磨。** 回放时直接喂入官方真值增量而非翻译值，脚本的排序质量与翻译质量被彻底解耦：给了正确增量仍然选错，问题在定价与前瞻；给了正确增量就选对，问题在翻译。两类缺陷不再互相掩盖，脚本的每一次调整都能被单独归因。
- **翻译误差模型的建模。** 把「预测增量 vs 实际增量」的残差按指标与预测值分箱，得到 5.4 分流所依赖的条件误差分布。它的意义不止于描述误差，而在于回答一个反事实问题：**在这样量级的翻译误差下，脚本还能否稳定达到目标成绩？** 若不能，就调整定价的稳健性——把权重从易误判的指标移向官方已给出数值的指标——或收紧弃权阈值。误差模型因此是「翻译不够准」与「决策不够稳」之间的调解机制。

三条回路彼此独立、可高速并行，单次评测的成本是「重放若干历史事件」而非「跑完一局」，且六个模块可以各自迭代而互不阻塞。方案的迭代频率因此不再受模拟器时长约束——这也是本方案能在有限时间内完成多轮结构性改进的直接原因。

## 八、局限与改进方向

### 8.1 已知局限

**翻译方向性错误无法根治。** 问卷作答本质上是 AI 对自然语言事件的语义判断，存在系统性方向误判的可能（如把「同事态度因做好事而转变」判成 S 增益）。决策置信度分析与语义纠偏是补救而非根治：纠偏时 Leader 需在缺少预测增量的条件下独立判断，认知负担上升，且其判断质量本身不再受符号约束保护。

**误差模型是边际的、且未经留出校准。** 它只给出各指标各自的条件误差分布，未建立指标间或选项间的联合分布，样本也导自历史问卷版本，与当前问卷并非严格同分布；R、普通事件的 D 以及未来剧情都不在覆盖范围内。因此「稳定率接近真实正确率」目前是一个**假设**而非已验证的结论（见 `decision_report.md` 3.4）。

**每事件 Token 开销显著高于无翻译基线。** 如 7.1 实测，本方案每事件约为基线的 2.9 倍，其中四分之三用于五个 teammate 的问卷作答。这笔开销的正当性依赖翻译准确率对成绩的实际贡献，而该贡献目前尚无对照实验直接量化；若翻译准确率的提升停滞，它将成为方案最主要的成本风险。

**R 指标不透明。** R 为隐藏态，问卷不可编辑，官方反馈只有少数档位且仅在特定事件出现，估算精度低于其他指标。当 R 的实际值偏离估算较多时，决策排序可能次优，而这一偏差无法在本局内被察觉。

**复核串行于决策之后。** review 阶段目前串行执行，无法与下一轮 observe 并行；若游戏 API 延迟较高，这会成为主要的时间瓶颈。

**无跨局泛化。** 工作流状态绑定单一 session，问卷修改不跨局保留，每局都需重新积累误判历史，前期翻译质量因此偏低。

**结构性死局的判据偏保守。** 三条判据均指向「已经出现极端后果」的情形，不涵盖翻译方向存在轻微偏差、但尚未造成极端后果的中间地带。这类情形目前只能依赖决策置信度分析间接捕获，而该分析本身又受限于误差模型未经校准，因此仍存在漏判空间。

### 8.2 潜在改进方向

- **跨局问卷知识迁移**：将高质量的问卷修改序列化为可复用的初始问卷版本，降低新局前期的误判率；
- **误差模型的联合化与在线校准**：引入指标间的联合误差分布，并用本局复核样本对先验做在线更新，使决策稳定率逐步逼近真实正确率；
- **翻译开销的自适应裁剪**：对置信度已明显偏高、或历史上从未出现方向误判的题型减少问卷题量，把节省下的 Token 重新分配给高风险事件；
- **R 指标强化**：基于选项关键词构建规则化的 R 先验，作为问卷判断的对照项，降低对单一语义判断的依赖；
- **并行 review-observe**：在 take_action 返回后立即触发 observe，与 review 脚本并行执行，压缩每轮的固定时间开销。
